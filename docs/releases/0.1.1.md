# HA Operator 0.1.1

This release adds passive shadow recording and replay tooling. Download the
archive, manifest, and validation evidence from the
[0.1.1 release](https://github.com/mikz/ha-operator/releases/tag/v0.1.1).
Use the attached evidence bundle to verify the archive hash and executed checks.
The [0.1.0 validation record](../scenarios.md#release-validation-record) applies
only to that earlier release's archive.

## Changes

- Add opt-in shadow tracing with bounded disk retention, sequence numbers,
  session snapshots, heartbeat records, loss reporting, and sanitized export.
- Add a persistent integration option that forces observe mode across every
  resource and prevents accidental live selection while recording.
- Add the admin-only, response-only `ha_operator.export_trace` action and journal health in
  downloadable diagnostics.
- Allow additional trace input entities without assigning actuator ownership.
- Preserve command context in dispatch observations without treating telemetry
  or external raw commands as a manual lease.
- Extend the isolated validation lab with trace replay and unreliable cellar-fan
  feedback. Release gates require the new scenario records and evidence files.
- Reject a package build that would silently replace the source or dependency
  provenance of an existing archive. Version checks include runtime, integration,
  baseline project, and compatibility project metadata.

Home Assistant support remains 2026.9.3 and 2026.9.4. The dependency versions are
unchanged. Project metadata changes from 0.1.0 to 0.1.1 in both lock files.

## Upgrade and passive observation

Install the new archive using the [release installation steps](../../README.md#install-a-release-archive).
Both trace options default to disabled for existing installations. To record
passively, enable `trace_enabled` and `shadow_lock` in the integration options.
Existing automations retain control of physical devices.

Trace recording is independent of durable request acceptance. Inspect export
health and sequence gaps before relying on a recording. The trace records the
inputs the integration observed; only a separate simulator run can establish
the effects of alternative commands. Passing the lab does not establish that
an untested physical device or optimistic wrapper supplies trustworthy feedback.

Before removing the shadow lock, inspect stored resource modes and intent and
complete the [migration runbook](../migration.md). Loading the locked integration
saves resources in observe mode. Unlocking requires separate, explicit live
activation for each resource before its valid saved intent can cause commands.

## Release validation

The release gate requires both locked source suites, per-module coverage, the four
guard mutation checks, HACS and hassfest, both packaged `all` runs, and a baseline
production-timing soak. The final record must identify the tested archive hash,
source revision, scenario results, image digests, and evidence bundle hash.
The release body reports the executed test counts and outcomes. Scenario names,
source tests, and the requirements on this page do not establish a passing run.
